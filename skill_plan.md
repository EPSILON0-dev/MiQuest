# Quest generation and app preparation plan

This is a plan, not an implementation. The goal is expressive, useful quest graphs generated by `skills/miquest-project`, with app support for emoji and page layouts.

## Planning guidelines for the skill

1. Understand the intended outcome and constraints. For a substantial project, decompose the outcome into major components, then recursively into subcomponents. Stop when a component has clear boundaries, outputs and dependencies and can be broken into independently verifiable work; do not split for its own sake. Small projects can go straight to quests.
2. Only after decomposition, create actionable quests for the smallest useful components. Keep each quest meaningful: use requirements within a quest for details that do not need independent dependencies or verification. Do not invent architecture when an important decision is unresolved; make the decision a focused quest where appropriate.
3. Add dependencies only for real blockers. Look for opportunities to work in parallel, then join branches when all inputs are actually needed. Do a separate integration pass to identify real interfaces, cross-component dependencies and integration work. Avoid obligatory research/plan/implement chains and artificial edges added for visual shape.
4. Use milestones for meaningful outcomes, with the necessary work as prerequisites. Reuse one shared quest across pages rather than duplicating a milestone or its completion history. Pages should represent useful components or views, not an arbitrary graph-size limit.
5. Give each quest a short, generally named title and a specific description. Write observable acceptance criteria as bullets using `Generic label — specific outcome`; distinguish otherwise ambiguous titles. Ensure milestones also have verifiable criteria.
6. Choose a relevant icon or emoji explicitly for every quest. Prefer distinct emoji within each page, but permit repeats when they best communicate the work or choices are exhausted. Shared quests keep the same icon on every page. This is guidance, not a validation error.
7. Choose a suitable layout per page: branching for independent work and joins, radial for a central outcome surrounded by component milestones, spiral for genuinely sequential work, and the existing default when appropriate. Graph dependencies remain authoritative regardless of shape.
8. Before delivery, check decomposition, actionable scope, real dependencies, parallelism, integration, milestone meaning, icon variety, observable criteria, graph validity and page membership. Present a concise text outline with page shapes, major branches, counts and material assumptions alongside the validated JSON. The existing import summary remains the in-app confirmation; a graph preview is not required for this phase.

Replace the current linear example with a small UI foundation → independent button/textbox/label → form example, and add an OS-style multi-page example with shared subsystem milestones, cross-component dependencies and a radial overview. Examples must validate against the final schema and demonstrate the actual supported layout and emoji representation.

## App constraints before implementation

- `backend/miquest/importer.py` accepts version 1 documents, validates icon names against `backend/miquest/icons.py`, and creates grid-like positions from dependency levels. Import does not accept page layout metadata or supplied positions. The frontend currently sends the same uploaded document to preview and create endpoints.
- `frontend/src/App.tsx` independently applies a left-to-right Dagre layout in the edit draft. Page positions already persist per appearance; `Page` has no layout field.
- Quest icons are stored as names; `frontend/src/icons.tsx` renders the bundled Lucide mapping and falls back to the compass. The editor uses `frontend/src/iconNames.ts`. The backend service and import validate the existing catalog, and the import schema enumerates it.
- Acceptance criteria are stored as plain text and rendered in the quest modal; verify that line breaks are visible before relying on bullet formatting.

## App work

### 1. Emoji and icons

- Keep existing icon names and saved quests working. Define one unambiguous representation for a supported emoji alongside named icons, with a bounded, documented validation rule or curated catalog shared by import and normal editing. Handle multi-code-point emoji deliberately; reject arbitrary text and unsafe markup. Avoid treating an unknown legacy icon name as emoji.
- Update backend validation for quest creation/editing and import, API contract and icon discovery as appropriate, and the generated import schema. Update the quest renderer and accessible editor picker/input so emoji display consistently in graph nodes, details and other icon locations. Preserve meaningful accessible labels; icons remain decorative where the quest title already labels the control.
- Decide and document the supported emoji set and fallback for unsupported system glyphs. Test actual rendering at node size on desktop and narrow screens. Do not add uniqueness constraints: repeated emoji are valid user data.

### 2. Page layout metadata and controls

- Add a persisted per-page layout preference with values for branching, radial and spiral. Existing saved pages default to branching; the new import contract is version 2 only.
- Add `bypassAutoLayout` and per-page quest positions to version 2 imports. With bypass enabled, preserve supplied positions exactly; validate complete, finite coordinates for every appearance and reject missing or invalid positions with a useful error rather than silently rearranging the page.
- Add the migration and update page models, domain services, API schemas/serialization, both OpenAPI contract copies, frontend model/API mapping, page creation/editing and import schema. Preserve metadata across reloads, editing, import, shared appearances and revision-checked draft saves.
- Expose an accessible, localized layout selector in edit mode and an explicit Auto layout action. Selecting or saving a preference must not silently move manually positioned quests; applying layout changes only the current page's draft positions and respects Save/Discard. Existing pages and their coordinates must survive migration and reload unchanged.

### 3. Layout behavior

- Implement the layout algorithms once in the frontend and reuse them for file import and the editor's Auto layout action. On file load, validate the input, calculate each page's positions from its chosen layout unless bypass is enabled, and send the resulting positions to the server as part of the import. The server validates and saves those positions atomically with the project; do not create the project first and update positions in a second request.
- Drop version 1 imports. Direct API callers must supply complete positions when creating an import, since the server does not run the frontend algorithms; preview accepts missing positions unless bypass is enabled.
- Confirm that preview validation accepts the source document before layout and that create validation accepts the prepared document; adjust the request contract as necessary. Keep preview and confirmation tied to the same uploaded data, and never replace explicitly bypassed positions during preparation.
- Branching should show dependencies clearly and allow parallel branches to converge. Radial should place the relevant outcome milestone centrally, with prerequisites outward; define a deterministic fallback for multiple/no suitable milestones, disconnected components and cross-page dependencies. Spiral should follow a genuinely linear chain towards its outcome; define a readable fallback for branches, multiple components and ambiguous ordering rather than changing dependencies.
- Produce deterministic finite positions, account for both quest and milestone dimensions, and avoid node overlaps for supported cases. Handle empty, single-node, disconnected and dense pages without errors. Shapes are presentation only: never mutate edges, quest identities, history or positions on other pages. Respect existing manual positions until the user explicitly applies a layout.
- Check larger graphs and edge readability. Auto-layout cannot guarantee a perfectly readable drawing for every dense graph; document fallback behavior and allow manual adjustment.

### 4. Skill and documentation

- Once the app contract is stable, update `skills/miquest-project/SKILL.md`, its JSON schema and examples with the planning workflow, emoji representation, page layout metadata, validation and text preview. Document the version 2 import requirement.
- Update the design and roadmap to reflect the newly requested emoji and specialized layouts, which extend the current v1 scope. Update user-facing import/editor documentation and `PROGRESS.md` with actual implementation and validation results.

## Suggested implementation order and checks

1. Agree on the emoji representation, layout values, and behavior for ambiguous graphs; add contract and migration tests first. For backend domain changes, follow red → green → refactor without weakening tests.
2. Implement and test emoji across backend validation, import, rendering and editing, including legacy named icons, invalid input, multi-code-point handling, accessibility and reload.
3. Add page metadata with migration, API and import tests, including existing projects and rejection of version 1 documents. Check revision conflicts and draft Save/Discard.
4. Implement frontend layout and import preparation; test deterministic coordinates, no node overlaps in representative inputs, graph invariants, page isolation, shared quests, empty/disconnected graphs and specified fallbacks. Confirm imported and manually applied layout behavior agree. Test bypass with exact position preservation, incomplete/invalid positions, direct API calls and atomic rollback on failure.
5. Update the skill and validate its examples against the real schema and importer. Review generated examples for real parallelism and requirements quality.
6. Run relevant backend and frontend checks and browser flows; inspect desktop and narrow screenshots for emoji, layout and controls. Record commands, results and limitations in `PROGRESS.md`; use a focused branch and PR without silently merging.

## Explicitly deferred

An interactive graph preview during generation or import, forced emoji uniqueness, uploads, and automatic page splitting are outside this plan. Text outlines and the existing import summary provide a lightweight review step.

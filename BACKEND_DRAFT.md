# MiQuest backend draft

Status: proposed implementation specification, not approval to begin Phase B.

DESIGN.md remains authoritative. UI prototype approval is still pending. This document proposes concrete contracts for the agreed scope; it does not change that approval gate. No backend, database, MCP, or deployment implementation is included.

## 1. Architecture and implementation choices

- Python 3.12+, FastAPI, Pydantic boundary schemas, synchronous SQLAlchemy 2.x, Alembic, SQLite, official Python MCP SDK, pytest, Ruff, and mypy.
- One Python package with REST and stdio MCP entry points. Both call the same service functions and access the same local SQLite file.
- One SQLAlchemy session per service operation. Services own transaction boundaries; adapters never commit halfway through an operation.
- No generic repository layer, dependency injection container, background worker, event bus, or server-side LLM.
- REST prefix: `/api/v1`. JSON field names use camelCase to match the existing frontend. Python attributes and SQL columns use snake_case.
- IDs: server-generated UUID strings, represented as TEXT in SQLite. All timestamps: UTC RFC 3339 strings with microseconds and `Z`, generated by the server.
- New databases start empty. Frontend fixtures remain test/demo data; do not seed production implicitly.

## 2. Proposed semantics to adopt before implementation

1. `fail` and `inconclusive` append history but preserve current completion. Only `reopen` clears completion. Thus the latest event is not necessarily the latest completion-changing event.
2. Editing title, description, criteria, icon, milestone, work state, or dependencies does not silently reopen a quest. History records what was evaluated; the UI can show historical completion alongside current locking.
3. Verification events capture the evaluated quest content and direct prerequisite completion snapshot. Later edits cannot rewrite the context of an old verdict.
4. Explicit permanent quest/project deletion removes associated verification history. “Append-only” prohibits editing or selectively deleting events while their quest exists. The destructive confirmation must disclose history loss. If retention after deletion is desired, change this decision before implementing; tombstones are outside this draft.
5. Human overrides may bypass prerequisites. A normal agent pass may not. Both agent and human reopening require a reason.
6. Home-page reassignment after removing an appearance must be explicit if the removed appearance was the home. Do not select an arbitrary remaining page.
7. Names need not be unique. IDs identify records; duplicate project/page names remain valid.
8. No real-time synchronization in v1. Refetch on focus and successful writes. Reject stale browser writes using project revisions.

## 3. Database schema

The following is the target logical DDL for the first Alembic migration. SQLAlchemy models must express the same keys and checks. Alembic's own `alembic_version` table is additional.

```sql
CREATE TABLE projects (
    id TEXT PRIMARY KEY NOT NULL,
    name TEXT NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 200),
    description TEXT NOT NULL DEFAULT '',
    revision INTEGER NOT NULL DEFAULT 0 CHECK (revision >= 0),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE pages (
    id TEXT PRIMARY KEY NOT NULL,
    project_id TEXT NOT NULL,
    name TEXT NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 200),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (id, project_id),
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);

CREATE TABLE quests (
    id TEXT PRIMARY KEY NOT NULL,
    project_id TEXT NOT NULL,
    title TEXT NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 200),
    description TEXT NOT NULL DEFAULT '',
    acceptance_criteria TEXT NOT NULL DEFAULT '',
    work_state TEXT NOT NULL DEFAULT 'not_started'
        CHECK (work_state IN ('not_started', 'in_progress', 'blocked')),
    completion_state TEXT NOT NULL DEFAULT 'none'
        CHECK (completion_state IN ('none', 'verified', 'overridden')),
    icon_name TEXT NOT NULL,
    milestone INTEGER NOT NULL DEFAULT 0 CHECK (milestone IN (0, 1)),
    home_page_id TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (id, project_id),
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    FOREIGN KEY (home_page_id, project_id)
        REFERENCES pages(id, project_id),
    FOREIGN KEY (home_page_id, id)
        REFERENCES quest_appearances(page_id, quest_id)
        DEFERRABLE INITIALLY DEFERRED
);

CREATE TABLE quest_appearances (
    page_id TEXT NOT NULL,
    quest_id TEXT NOT NULL,
    project_id TEXT NOT NULL,
    position_x REAL NOT NULL,
    position_y REAL NOT NULL,
    PRIMARY KEY (page_id, quest_id),
    FOREIGN KEY (page_id, project_id)
        REFERENCES pages(id, project_id) ON DELETE CASCADE,
    FOREIGN KEY (quest_id, project_id)
        REFERENCES quests(id, project_id) ON DELETE CASCADE
);

CREATE TABLE dependencies (
    quest_id TEXT NOT NULL,
    depends_on_quest_id TEXT NOT NULL,
    project_id TEXT NOT NULL,
    PRIMARY KEY (quest_id, depends_on_quest_id),
    CHECK (quest_id <> depends_on_quest_id),
    FOREIGN KEY (quest_id, project_id)
        REFERENCES quests(id, project_id) ON DELETE CASCADE,
    FOREIGN KEY (depends_on_quest_id, project_id)
        REFERENCES quests(id, project_id) ON DELETE CASCADE
);

CREATE TABLE pins (
    project_id TEXT NOT NULL,
    quest_id TEXT NOT NULL,
    sort_order INTEGER NOT NULL CHECK (sort_order >= 0),
    PRIMARY KEY (project_id, quest_id),
    UNIQUE (project_id, sort_order),
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    FOREIGN KEY (quest_id, project_id)
        REFERENCES quests(id, project_id) ON DELETE CASCADE
);

CREATE TABLE verifications (
    id TEXT PRIMARY KEY NOT NULL,
    quest_id TEXT NOT NULL,
    sequence INTEGER NOT NULL CHECK (sequence > 0),
    verdict TEXT NOT NULL
        CHECK (verdict IN ('pass', 'fail', 'inconclusive', 'override', 'reopen')),
    actor TEXT NOT NULL CHECK (actor IN ('agent', 'human')),
    evidence TEXT NOT NULL DEFAULT '',
    reasoning TEXT NOT NULL CHECK (length(trim(reasoning)) > 0),
    snapshot_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    UNIQUE (quest_id, sequence),
    CHECK (verdict <> 'pass' OR
        (actor = 'agent' AND length(trim(evidence)) > 0)),
    CHECK (verdict <> 'override' OR actor = 'human'),
    CHECK (verdict NOT IN ('fail', 'inconclusive') OR actor = 'agent'),
    FOREIGN KEY (quest_id) REFERENCES quests(id) ON DELETE CASCADE
);

CREATE INDEX ix_pages_project ON pages(project_id);
CREATE INDEX ix_quests_project ON quests(project_id);
CREATE INDEX ix_appearances_quest ON quest_appearances(quest_id);
CREATE INDEX ix_dependencies_prerequisite ON dependencies(depends_on_quest_id);

CREATE TRIGGER verification_no_update
BEFORE UPDATE ON verifications
BEGIN
    SELECT RAISE(ABORT, 'verification records are immutable');
END;
```

### Constraint details

- The deferred home-appearance foreign key requires every surviving quest to have a valid home appearance at commit, which also guarantees at least one appearance. Quest creation inserts the quest and initial appearance in one transaction.
- `project_id` on appearances and dependencies is intentional: composite foreign keys enforce project ownership without trusting service validation alone.
- The quest/home-page cycle means ORM mappings must use explicit foreign keys and avoid automatic relationship persistence ordering; service inserts/deletes and flushes are explicit. Test migration creation, creation transactions, page deletion, and whole-project deletion on real SQLite before accepting this schema.
- Permanent project deletion explicitly deletes its quests before its pages, then deletes the project. Page deletion rehomes/deletes affected quests before removing the page. Do not rely on ambiguous cascade order through the home-page relationship.
- Cycles, valid icon names, finite positions, input lengths, pin permutation validity, and state transitions are service/boundary validations.
- No event update/delete API exists. The update trigger adds protection against accidental ORM edits; direct database access remains trusted, including backup/restore and migrations.
- Verification ordering uses `sequence`, allocated under the write lock, rather than timestamps.

## 4. Transactions, concurrent writes, and revisions

Configure foreign keys on every connection, WAL on database initialization, a 5-second busy timeout, and explicit transaction control appropriate to the pinned Python/SQLAlchemy versions.

Every mutation follows this sequence:

1. Open a session and acquire a SQLite write transaction with `BEGIN IMMEDIATE` before reading validation state.
2. Load the owning project and compare `expectedRevision` when provided.
3. Validate all IDs, ownership, membership, graph rules, and transition rules.
4. Apply the entire operation, including cached completion/history changes.
5. Increment project `revision` once for a real change and update its `updated_at`.
6. Flush and commit before returning success. Roll back on every error.

All writers, including stdio MCP, use this path. SQLite's process-wide file locking closes the race where two processes each validate an edge against an old DAG. Readers use short, explicit read transactions to return a consistent graph snapshot.

Existing-project REST mutations require `expectedRevision`; project creation does not. MCP mutations accept it optionally: agents can request concurrency checks, while omitted values still validate against the latest state inside the serialized transaction. A revision mismatch returns `stale_revision` with `currentRevision`; there is no automatic replay of a destructive operation.

Project-wide revisions intentionally cause conservative conflicts even for unrelated edits. The frontend refetches on conflict and asks the owner to retry. This is sufficient for one owner plus an external agent; per-record versions can be added only if actual contention warrants them.

A database lock timeout becomes `database_busy`, not an unexplained HTTP 500. No transaction remains open during agent reasoning or network calls.

## 5. Shared JSON contracts

### Entities

```ts
type Project = {
  id: string; name: string; description: string;
  revision: number; createdAt: string; updatedAt: string;
};
type Page = {
  id: string; projectId: string; name: string;
  createdAt: string; updatedAt: string;
};
type Quest = {
  id: string; projectId: string; title: string; description: string;
  acceptanceCriteria: string;
  workState: 'not_started' | 'in_progress' | 'blocked';
  completionState: 'none' | 'verified' | 'overridden';
  icon: string; milestone: boolean; homePageId: string;
  createdAt: string; updatedAt: string;
};
type QuestView = Quest & {
  unlocked: boolean;
  unsatisfiedPrerequisiteIds: string[];
  status: 'locked' | 'available' | 'in_progress' | 'blocked'
    | 'verified' | 'overridden';
};
type Appearance = { pageId: string; questId: string; x: number; y: number };
type Dependency = { questId: string; dependsOnQuestId: string };
type Pin = { projectId: string; questId: string; sortOrder: number };
type Verification = {
  id: string; questId: string; sequence: number;
  verdict: 'pass' | 'fail' | 'inconclusive' | 'override' | 'reopen';
  actor: 'agent' | 'human'; evidence: string; reasoning: string;
  snapshot: {
    title: string; description: string; acceptanceCriteria: string;
    prerequisites: {
      questId: string; completionState: Quest['completionState'];
      latestCompletionEventId: string | null;
    }[];
  };
  createdAt: string;
};
```

`unlocked` means all direct prerequisites are verified or overridden. No prerequisites means unlocked. Preserve the existing frontend rule: a historically completed but currently locked prerequisite still has completion state verified/overridden; transitive locking is not substituted for completion. `status` is locked first, then completion, then work state (`not_started` maps to available). Completion badges use `completionState` independently.

### Responses

Reads use `{ data: ... }`. Existing-project reads also include `projectRevision`. Mutation responses use `{ data: ..., projectRevision: number }`; successful deletion returns `{ data: { deletedId: string }, projectRevision: number }`. Project deletion has no surviving revision and returns only `data`. Project creation returns the new project at revision 0.

List order is deterministic: projects/pages/quests by `(createdAt, id)`, pins by `sortOrder`, verifications by ascending `sequence`, dependencies by both IDs, appearances by `(pageId, questId)`.

### Error response

```json
{
  "error": {
    "code": "dependency_cycle",
    "message": "This dependency would create a cycle.",
    "details": { "questId": "...", "dependsOnQuestId": "..." }
  }
}
```

| HTTP | Codes |
|---|---|
| 404 | `project_not_found`, `page_not_found`, `quest_not_found`, `appearance_not_found` |
| 409 | `dependency_exists`, `dependency_cycle`, `quest_would_be_orphaned`, `home_page_required`, `prerequisites_unsatisfied`, `stale_revision` |
| 422 | `invalid_input`, `cross_project_reference`, `self_dependency`, `invalid_home_page`, `invalid_pin_order`, `evidence_required`, `reason_required`, `confirmation_required`, `invalid_icon` |
| 503 | `database_busy` (with `Retry-After: 1`) |
| 500 | `internal_error` (no SQL, stack trace, or local paths in response) |

Normalize Pydantic request errors to `invalid_input` with field paths. Reject unknown request fields. Log unexpected errors on stderr with a request identifier, returned as `requestId` in the error envelope.

### Validation limits

Names/titles: trimmed, 1–200 characters. Description and acceptance criteria: up to 100,000 characters each. Reasoning: trimmed, 1–20,000 characters. Evidence: up to 100,000 characters; whitespace-only is invalid for pass. Coordinates: finite numbers with absolute value at most 1,000,000. No HTML interpretation, URL fetching, or file reads from evidence.

Use one checked-in icon-name manifest shared with frontend generation/tests, based on the current bundled icon list. Default `compass`; unknown names are rejected. IDs, ownership, actor, timestamps, completion, and revision are never generic quest-edit fields.

## 6. REST endpoints

All paths below are relative to `/api/v1`. Mutation bodies on existing projects include `expectedRevision: integer >= 0`, even where omitted from the table for readability. DELETE requests use JSON bodies; the API client must send them explicitly.

### Projects and metadata

| Method | Path | Request | Response data |
|---|---|---|---|
| GET | `/projects` | — | `Project[]` |
| POST | `/projects` | `{name, description?}` | `Project` (201) |
| GET | `/projects/{projectId}` | — | `Project` |
| PATCH | `/projects/{projectId}` | `{name?, description?, expectedRevision}` | `Project` |
| DELETE | `/projects/{projectId}` | `{expectedRevision, confirmDelete:true}` | `{deletedId}` |
| GET | `/icons` | — | `{defaultIcon, names:string[]}` |
| GET | `/projects/{projectId}/graph` | — | Full project graph below |

A project may have zero pages; page creation is an explicit action in the existing empty-state flow.

### Pages and appearances

| Method | Path | Request | Response data |
|---|---|---|---|
| GET | `/projects/{projectId}/pages` | — | `Page[]` |
| POST | `/projects/{projectId}/pages` | `{name, expectedRevision}` | `Page` (201) |
| GET | `/pages/{pageId}` | — | `Page` |
| PATCH | `/pages/{pageId}` | `{name, expectedRevision}` | `Page` |
| DELETE | `/pages/{pageId}` | Page deletion plan below | `{deletedId}` |
| GET | `/pages/{pageId}/graph` | — | Page graph below |
| PUT | `/pages/{pageId}/quests/{questId}` | `{x,y,expectedRevision}` | `Appearance` |
| PATCH | `/pages/{pageId}/quests/{questId}` | `{x,y,expectedRevision}` | `Appearance` |
| DELETE | `/pages/{pageId}/quests/{questId}` | `{expectedRevision,newHomePageId?}` | Updated `Quest` |
| PUT | `/pages/{pageId}/positions` | `{expectedRevision,positions:[{questId,x,y}]}` | `Appearance[]` |

PUT appearance adds an existing quest to a same-project page or updates its position. PATCH requires the appearance to exist. Neither changes home page. Batch positions update only existing appearances, reject duplicate quest IDs, and commit all or none. An empty batch is valid and leaves the revision unchanged.

Removing a final appearance returns `quest_would_be_orphaned`; to move it, first add the destination appearance, then remove the old one with `newHomePageId`. Deleting the quest globally is a separate confirmed operation.

Page deletion body:

```json
{
  "expectedRevision": 12,
  "confirmDelete": true,
  "questActions": [
    { "questId": "quest-a", "action": "move", "targetPageId": "page-b", "x": 120, "y": 80 },
    { "questId": "quest-b", "action": "rehome", "targetPageId": "page-c" },
    { "questId": "quest-c", "action": "delete", "confirmDelete": true }
  ]
}
```

- `move`: add an appearance on another same-project page and assign it as home if necessary. Explicit coordinates prevent hidden positioning choices.
- `rehome`: target must already contain the quest; changes the home before removal.
- `delete`: permanent quest deletion everywhere, including history; requires its own confirmation.
- Require an action for every quest that would lose its last appearance or home. Other quests simply lose this page's appearance.
- Reject duplicate actions, actions for absent quests, invalid destinations, and incomplete plans before applying anything.

### Quests and dependencies

| Method | Path | Request | Response data |
|---|---|---|---|
| GET | `/projects/{projectId}/quests` | — | `QuestView[]` |
| POST | `/projects/{projectId}/quests` | Creation body below | `{quest:QuestView,appearance:Appearance}` (201) |
| GET | `/quests/{questId}` | — | Quest details below |
| PATCH | `/quests/{questId}` | Editable fields below + `expectedRevision` | `QuestView` |
| DELETE | `/quests/{questId}` | `{expectedRevision,confirmDelete:true}` | `{deletedId}` |
| POST | `/quests/{questId}/dependencies` | `{dependsOnQuestId,expectedRevision}` | `Dependency` (201) |
| DELETE | `/quests/{questId}/dependencies/{prerequisiteId}` | `{expectedRevision}` | `{questId,dependsOnQuestId}` |

Creation requires `{title,pageId,x,y,expectedRevision}`; optional fields are `description`, `acceptanceCriteria`, `workState`, `icon`, and `milestone`. The initial page is the home page. Completion starts as `none`. Project ownership comes from the route.

PATCH accepts only `title`, `description`, `acceptanceCriteria`, `workState`, `icon`, `milestone`, and `homePageId`; home must be an existing same-project appearance. Reject an empty patch. No project transfer endpoint.

Quest details: `{quest:QuestView,appearances:Appearance[],prerequisites:QuestView[],nextQuests:QuestView[]}`. All neighbors are included regardless of page. History is fetched separately on expansion.

Dependency direction is always prerequisite → dependent, represented as `{questId: dependent, dependsOnQuestId: prerequisite}`. To add `A depends on B`, reject if walking B's prerequisite chain reaches A. Use an iterative visited-set traversal over the project's adjacency map; no graph dependency is needed. Removing a missing edge is an idempotent success.

### Pins

| Method | Path | Request | Response data |
|---|---|---|---|
| GET | `/projects/{projectId}/pins` | — | `Pin[]` |
| PUT | `/projects/{projectId}/pins/{questId}` | `{expectedRevision}` | `Pin` |
| DELETE | `/projects/{projectId}/pins/{questId}` | `{expectedRevision}` | `{questId}` |
| PUT | `/projects/{projectId}/pin-order` | `{questIds:string[],expectedRevision}` | `Pin[]` |

Pinning an existing pin is a no-op; a new pin appends. Unpinning a missing pin is a no-op. Reorder requires an exact permutation of current pins, with no duplicates. Rewrite pins transactionally to avoid transient unique-order collisions. Orders are compacted to `0..n-1` after removal/deletion; all rewriting is within the same mutation transaction.

### Verification

| Method | Path | Request | Response data |
|---|---|---|---|
| GET | `/quests/{questId}/verifications` | `?afterSequence=0&limit=50` | `{items:Verification[],nextAfterSequence:number|null}` |
| POST | `/quests/{questId}/override` | `{reason,confirmOverride:true,expectedRevision}` | `{quest:QuestView,verification:Verification}` (201) |
| POST | `/quests/{questId}/reopen` | `{reason,expectedRevision}` | `{quest:QuestView,verification:Verification}` (201) |

History limit: 1–200. Events are oldest first, with a cursor only when more remain. Browser override/reopen actor is set by the adapter to `human`; callers cannot supply it. An already-open quest cannot be reopened (`invalid_input`). Repeated overrides append distinct events because each represents a deliberate human decision.

There is no REST agent-pass endpoint in v1. Agent verdicts enter through MCP. The actor labels describe the entry point and supplied provenance, not authenticated identity; the network boundary and invoking agent are trusted.

### Graph payloads

Full project graph:

```ts
{
  project: Project;
  pages: Page[];
  quests: QuestView[];
  appearances: Appearance[];
  dependencies: Dependency[];
  pins: Pin[];
}
```

Page graph:

```ts
{
  project: Project;
  page: Page;
  quests: QuestView[]; // quests with an appearance on this page
  appearances: Appearance[]; // only this page
  dependencies: Dependency[]; // both endpoints on this page

```

External links represent each edge with exactly one endpoint on the page; no unrelated external edges are included. Do not include all verification histories in graph reads.

## 7. Verification state machine

| Operation | Preconditions | Completion afterward | Work state |
|---|---|---|---|
| Agent `pass` | Nonempty evidence/reasoning; direct prerequisites completed | `verified` | Preserved |
| Agent `fail` | Nonempty reasoning | Preserved | Preserved |
| Agent `inconclusive` | Nonempty reasoning | Preserved | Preserved |
| Human override | Reason + explicit confirmation | `overridden` | Preserved |
| Agent/human reopen | Reason; currently completed | `none` | `not_started` |

Each operation appends a snapshot event and updates any completion/work-state cache atomically. A pass may supersede an override. A locked previously completed quest can receive fail/inconclusive/reopen, but cannot receive a new pass. Completion is not erased when adding dependencies or reopening upstream quests.

## 8. MCP contract

Use the official SDK, pinned to a tested stable release before implementation. stdio only. No HTTP listener or remote MCP authentication implementation.

Every tool maps to one service operation. Input JSON uses the same camelCase names and validation rules as REST. Tool names use snake_case. Existing-project mutations accept optional `expectedRevision`; destructive operations still require confirmation booleans. Return the same success/error data structures as REST, using the SDK's structured tool output and error signaling, without invented HTTP statuses in MCP.

The invoking client can run the installed MCP entry point on the trusted host or through `docker compose exec -T app ...` using the same application image. Do not mount the Docker socket into the app. Document exact commands once packaging is implemented and tested.

## 9. Frontend integration

- Add one small typed API client and one state hook for loading project data, sending mutations with the current revision, and refetching after success. Retain existing components and semantic CSS.
- Initially fetch projects, restore the saved target if it still exists, then load the active project's full graph. Project graphs are small enough for the agreed tens-to-hundreds scale; no normalized cache dependency is needed.
- Load verification history only when expanded. Use the paged history route without discarding previously displayed events.
- Replace every fixture mutation: project/page CRUD, quest editor saves/deletes, appearance/home changes, dependencies, pins/order, override/reopen, node drag, and automatic layout.
- Submit node position on drag-end. Submit auto-layout as one batch. Keep transient drag positions local until commit; roll back/refetch on failure.
- Serialize browser mutations so each uses the revision returned by the last successful one. Disable duplicate submission controls while pending. Preserve form text on errors.
- Refetch on window focus and provide an explicit refresh control. Do not overwrite a dirty editor draft during a refetch. Stale submission preserves the draft and reports that server data changed.
- Edit mode, selection/modal state, sidebar state, viewports, and last-view restoration remain local. Edit mode still resets to off after reload.
- Never silently fall back to fixtures if the backend fails. Show retryable loading errors and the genuine empty state.

## 10. Runtime, security boundary, and operations

Configuration is limited to database path, bind host/port, allowed hostnames, and log level. Default local database: `./data/miquest.sqlite3`; container path: `/data/miquest.sqlite3`.

- Serve built frontend assets and `/api/v1` from the same FastAPI application. The SPA fallback must not swallow unknown `/api` paths. Development proxy targets the local API.
- No wildcard CORS. Validate Host against configured local/tailnet hostnames. Reject browser mutation requests with a foreign Origin; allow non-browser origin-less requests within the trusted deployment boundary. JSON-only mutation routes plus Origin checks protect against cross-site browser writes; this is not app authentication.
- Bind published host port to `127.0.0.1`; browser access uses Tailscale Serve and tailnet access controls. No public unauthenticated listener.
- One app worker initially. MCP may run as a separate trusted process against the same local file. Keep the database off NFS/SMB.
- Non-root container, read-only root filesystem where practical, writable `/data` plus temporary runtime storage only. No uploads, arbitrary execution, evidence URL fetching, privileged mode, or host socket mount.
- Run Alembic as an explicit startup step before serving requests. MCP startup checks schema compatibility and fails clearly instead of racing to migrate it. Do not silently recreate a missing configured production database on a path typo.
- `GET /healthz` returns `{status:"ok"}` when the process responds. `GET /readyz` checks database access and schema compatibility; return 503 if unavailable, without exposing filesystem paths.
- Back up using Python's SQLite backup API into a separate destination file; do not copy only the live main database file while WAL is active. Restore with all writers stopped, verify integrity and migration version, then restart. Document and test an actual backup/restore cycle.
- No evidence content in routine logs. Log operation/error identifiers, not full request bodies.

## 11. Tests and delivery sequence

All nontrivial domain behavior follows red → green → refactor. Record the intended failing assertion before implementing the feature; do not weaken existing tests.

| Milestone | Required evidence |
|---|---|
| Schema and migrations | Empty DB upgrade; foreign-key checks; invalid cross-project rows rejected; deferred home membership enforced at commit; reopen file preserves data; migrate representative populated DB |
| Membership and CRUD | Shared quest edits affect all appearances; positions remain independent; explicit home reassignment; last appearance rejected; page deletion plans are atomic; project deletion works through circular references; permanent deletion cleanup |
| DAG and concurrency | Self/cross-project/duplicate/cyclic edges rejected; cycles spanning pages; two independent connections/processes cannot concurrently create a cycle; failed operations leave revision/data unchanged |
| Pins | Append, idempotent pin/unpin, exact permutation validation, collision-free reorder, cleanup and compaction after quest deletion |
| Verification | Every state-machine row; missing evidence/reason; locked pass rejected; snapshots survive edits; events immutable; completion/event rollback together; historical completion persists through relocking |
| REST | Typed payloads, forbidden fields, all error mappings, stale revision, confirmation rules, finite coordinates, graph cross-tree links, history pagination, commit failures surfaced before success |
| MCP | Real stdio initialization/discovery/tool calls; schema validation; structured failures; agent cannot submit override/actor; REST and MCP see the same persisted changes |
| Frontend/E2E | Create/edit/reload; drag and batch layout persistence; shared identity; membership deletion safeguards; cycle error; override/reopen/history; stale save preserves draft; API failure recovery; agent edits visible after refresh |
| Delivery | Clean build/lint/type/tests; desktop/narrow screenshots inspected; app/container restart persistence; backup/restore; documented private access and stdio launch |

Use temporary file-backed SQLite databases for transactional/concurrency tests; an in-memory database is not a substitute for multi-connection locking tests. Test domain services directly, adapter error mapping separately, and critical workflows end to end. No network dependency in test assertions.

Deliver focused branches/PRs: persistence/domain, REST/frontend, MCP, and packaging/acceptance. Verification domain rules belong with persistence/domain, before adapters can expose completion mutations. Update PROGRESS.md with actual commands, results, and blockers at each milestone. Never merge silently.
